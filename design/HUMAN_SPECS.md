# Human Specs — the spec the human writes

The human spec convention the agent expects, reads, and checks. The scaffold is generated by the AI Coding Kit (`/spec micro|quick|new|full`, `bin/spec_workflow.py`); this file states what a finished spec carries. The agent's side — reading the spec, writing `agent_tasking.md` — is `AGENT_TASKING.md`.

## Whether and which spec

- Proportionality gate — no spec for a change one sitting can hold: single file, no new interface, no cross-module impact, no team decision.
  - Durable-decision test: will anyone need to understand *why* in a month? No → no spec.
- Blast radius decides whether: touches core, the data model, or more than one service → a spec, read end to end and explicitly approved before work starts.
- Kind and complexity decide the tier; hours are a proxy, not the line.
  - Micro (`/spec micro`, under a day): bug fixes, docs, config changes.
  - Quick (`/spec quick`, one to three days): a small feature that can be summed up in a few words; API endpoints.
  - Standard (`/spec new`, three to ten days): several components, or new patterns or tech.
  - Full (`/spec full`, beyond): cross-team impact.
- Tier mismatch — a multi-service change under a micro or quick spec — is a large divergence; the agent asks before tasking.
- Overlap check first: scan `specs/` for a duplicate or related spec before creating one.

## File location

- `specs/<YYYYMMDD>-<slug>/` at the repo root, one directory per spec.
  - Micro: `micro-spec.md`.
  - Quick: `quick-spec.md`.
  - Standard and full: `requirements.md`, `design.md`, `tasks.md`.
- The agent's tasking file sits beside it: `specs/<YYYYMMDD>-<slug>/agent_tasking.md` (`AGENT_TASKING.md` § Tasking file).

## Every tier

- Opens with the three questions, answered in one line each: what ships, when, who owns it.
  - The scaffold supplies `**What:**`; the human adds `**When:** <date>` and `**Owner:** <who>` beside it.
  - A spec that cannot answer them is a draft.
- Answers, before review: who the user is, what problem this solves, the alternatives and why not those, how success is measured.
- States the boundary: which modules change and which do not.
  - A change that crosses the boundary — an "extension" that rewrites core — is a large divergence; the agent asks.
- Names the alternatives considered and why not, one line each; the minimal fix is one of them.
- Requirements describe outputs and outcomes from the user's perspective, not the implementation.
- Statements follow SOLID, open/closed in particular: what this change adds or does, not the module's inventory (`~/agents/style/DOT_POINT_SRP.md` § SOLID statements).
- Durable references: full repo paths, function and class names; no line numbers.
- Written in dot-point-srp style; no hand-wrapped prose.

## Micro spec

The scaffold's fields, each one line unless noted:

- `**What:**` — the change in one sentence.
- `**When:**`, `**Owner:**` — added by the human.
- `**Why:**` — business value or user need.
- `**How:**` — the implementation steps, as a short list.
- `**Acceptance:**` — pass/fail criteria, written as observable facts.
- `**Not changing:**` — the boundary: known non-goals, deferred items, modules left alone.
- `**Alternatives:**` — added by the human: the other ways considered and why not.
- `## Related` — links to overlapping or upstream specs.

## Quick spec

- `## Problem` — the observed problem in one or two sentences, then `**Decision:**`, `**Success:**`, `**Next:**`; `**When:**` and `**Owner:**` added beside them.
- Scope checkpoint — in and out of scope, and the boundary.
- `## Requirements` — `- [ ] **R<n> — <title>:** <specific, testable behaviour>`; one requirement per line; error and edge behaviour get their own `R<n>`.
- `## Implementation approach` — the existing component reused and the minimal change; the material trade-off; the alternatives and why not.
- `## Implementation tasks` — `- [ ] **T<n> — <name>**` with estimate, dependency, verification. Proposed by the agent from its tasking file, written on the human's approval.
- `## Verification` — focused and regression checks with expected results.
- `## Related`.

## Standard and full specs

- Three phases, three files: `requirements.md`, `design.md`, `tasks.md` (`/spec new` lean, `/spec full` detailed).
- Requirements: numbered `R<n>`, user perspective, out of scope listed, every error case listed.
- Design: interfaces, components, data flow, constraints, key decisions with reasoning; sets direction without dictating every line.
- Tasks: 1–4 hours each, ordered by dependency, one commit per task.
- Use cases, where written: `- [ ] U<n>: <scenario> (R<ids>)`; every requirement appears in at least one.
- Acceptance checklist, where written: `X1` code solves the stated goal; `X2` behaviour matches each requirement; `X3` scope boundaries respected; `X4` interfaces match the design; `X5` error cases handled as specified; `X6` no TODOs or placeholders.

## Authorship

- The human owns the content; the agent may hold the pen on approval — the `task.md` contract (`~/agents/review/TASK_FILE.md`, `AGENT_TASKING.md` § Authorship).
- A gap or conflict in the spec → the agent asks; the human supplies the words.
- A spec is reviewed when someone other than the author has read it end to end and replied in the thread. Silence is not approval.

## The spec is not a tracker

- The spec states the target contract — the settled truth, written as if it had always been so.
- No status markers in spec prose: no `DONE`, `Status:`, `REVERTED`, `NOT IMPLEMENTED`.
- No edit history in spec prose: no "corrected", "rewritten", "was X now Y", no rebuttal of review claims.
- Each kind of record has its own home:
  - What changed and when → git history of the spec file.
  - Why a direction was chosen or reversed → `task.md` `# DECISIONS` (`~/agents/review/TASK_FILE.md`).
  - Review claims and their outcomes → the review store (`~/agents/review/ISSUE_TRACKING.md`).
  - Implementation progress → checkbox state on `R<n>` / `T<n>` lines; the agent's `A<n>` lines in `agent_tasking.md`.
- Tracking surfaces are checkbox flips, not prose annotations.

## Validation

- `/check-spec` (`~/agents/skills/CHECK_SPEC.md`) checks a spec directory against this file: `scripts/validate_spec.py` for the mechanical rules, then a judgment pass.
- A spec that fails it is a draft.
